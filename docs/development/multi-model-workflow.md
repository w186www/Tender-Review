# 跨软件模型分工与仓库派工

适用本仓库的开发过程。依据ADR-0009；业务需求、契约、安全要求和AGENTS继续生效。模型只需读取当前任务需要的文件，不复制完整聊天或反复读取整份Word。

## 分工

| 工作 | 默认负责人 | 产物 |
|---|---|---|
| 资料盘点、方案草案、未知问题清单 | DeepSeek V4.1 Flash | 派工单指定的方案与来源记录 |
| 契约、安全边界、迁移、法规适用口径、验收设计审定 | GPT-6.1 Sol 高 | 仓库方案/契约/ADR，设计审查结论 |
| 已审定契约下的常规实现、测试与修复 | DeepSeek V4.1 Flash | 任务分支提交、测试证据、交接单 |
| 权限、事务并发、复杂恢复等核心实现 | GPT-6.1 Sol 中/高 | 具体实现与针对边界的验证 |
| 合并前独立审查、最终任务归档 | GPT-6.1 Sol 高 | 绑定提交SHA的审查结论与完成证据 |

这是初始分工。若某模型在实际任务中反复遗漏关键问题，可调整派工负责人并记录原因，不把型号名字当作质量证明。开发模型与TASK-0008将选择的产品运行时模型是不同事项。

若核心实现转给GPT，独立代码审查转给DeepSeek或另一位实际审查者，再由GPT作为项目维护者核验和收尾。最终维护者与独立审查者可以不同；不能把GPT对自己刚写代码的检查称为独立审查。DeepSeek复核提示词见prompts/deepseek-review-core.md。

## 文件职责

| 文件 | 用途 |
|---|---|
| AGENTS.md | 所有软件的共同规则，必须显式读取 |
| PROJECT_STATE.md | 当前项目与下一步，不代替任务详单 |
| tasks/active/TASK-*.yaml | 需求、依赖、允许路径、局部验收；唯一正式任务 |
| tasks/dispatch/TASK-####.md | 当前阶段、分工、设计边界、允许交付物和下一动作 |
| tasks/handoffs/TASK-####.md | 实施者提交SHA、验收映射、命令结果与未完成事项 |
| tasks/reviews/TASK-####.md | 设计/代码审查范围、确切提交SHA、问题与最终结论 |
| docs/development/prompts/ | 不同软件可重复使用的启动提示词 |

派工/交接/审查Markdown是工程记录，没有自动执行、自动锁或CI状态机；不能声称已部署自动多Agent平台。任务YAML状态仍仅planned/in_progress/blocked/completed，不能私加待审查枚举。

## 从派工到完成

1. 任务准备者检查依赖，建立派工单，列出实施阶段与设计待定项。跨模块契约未明确时，先派资料盘点和设计草案，暂不改业务代码。
2. 实施者在派工单记录实际base SHA、分支、写入者、软件和阶段；把正式TASK置in_progress。核对已有未提交工作，不覆盖其他人内容。
3. 设计审查者读取草案与必要依据，在审查单记录准确design commit SHA以及approved/changes_requested。契约或安全设计发生变化需重新审定。设计通过后派工单改为implementation。
4. 实施者按范围完成代码、相应测试和启动说明，运行完整verify.ps1和任务要求的专项检查。失败修复后重跑；没有工具/网络权限时记录未执行原因，不能用静态阅读代替运行。
5. 实施者把实际日志摘要写入版本化验收记录，交接单逐项对应acceptance_checks，记录base/head SHA、复现步骤、迁移/回滚和未完成。提交代码和证据后记录code candidate SHA；交接单可在下一独立文档提交中引用它，避免提交哈希自引用。将派工阶段设review，正式TASK保持in_progress，然后停止写入。
6. 审查者在同一候选版本核对契约、实际代码、调用链和测试，关注漏检、错误证据、权限/并发/恢复等边界；核对本地与远程结果各自对应SHA。若候选之后有交接文档提交，实际checkout可为交接HEAD：必须检查candidate..HEAD差异仅为已列明的交接/任务进度/验证记录，记录候选SHA与交接HEAD，审查目标绑定实际交接HEAD。不能把后续代码、契约或设计变化当作纯记录忽略；存在这类变化需新候选。审查不要求重新实现整个任务。
7. 有阻断问题时，在审查单写changes_requested与复现/文件行号/验收要求，交回实施者修复。每次代码变化使原代码审查结论失效；由审查者重新记录新的SHA。不得用模型声称“已通过”代替实际证据。
8. 最终审查者确认局部验收及required checks真实通过，在审查单记录approved和实际负责人，填写正式TASK证据并归档，更新PROJECT_STATE/CHANGELOG；归档后重跑完整门禁。合并/推送按用户已有授权执行，发布部署另按release-process.md。

不必为每个小改动做完整模型审查；先集中实现和本地排错，再进行一轮候选版本审查。但每次提交前必须遵守AGENTS，不能靠降低或跳过门禁减少成本。

## 两个软件如何接手

用户负责把启动提示词发送到另一软件，或把仓库任务路径交给该软件。仓库本身不会通知另一个模型，当前助手也不会未经授权向另一软件发消息。

**共享同一目录：**两个软件都打开本仓库根目录，先检查git status和当前分支。前一软件停止任务、完成提交并明确交接后，后一软件才读取或写入；不能让两个软件同时自动修复同一目录。分支切换前确认无未提交改动；遇到其他人的未提交内容先停止写入并说明。

**不同checkout/不同电脑：**两端使用同一远程仓库。实施从最新main建立work/TASK-####任务分支并push该分支；审查端在干净工作区fetch，切到同一分支，核对交接记录的候选SHA后审查。修复继续推送同分支。最终通过后才合入main；不对共享分支force push，也不使用reset --hard清除未提交内容。

最小只读核对命令：

```text
git status --short
git branch --show-current
git rev-parse HEAD
```

远程模式在干净工作区更新main时使用git pull --ff-only。若发生分叉，保存并报告现状，不能强行重置。具体软件是否自动读取AGENTS不能假设；启动提示词应明确要求读取。没有仓库读写、终端或Git能力的软件只能提供建议，不能冒充已经执行任务。
